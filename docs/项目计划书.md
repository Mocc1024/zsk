## 一、项目定位与目标

### 1.1 项目定位

ZSK 是一套「内容生产 → 内容管理 → 内容分发 → 数据反馈」闭环的内容管理平台。平台后端基于 ThinkPHP 8 提供 RESTful API，前端后台基于 React 18 + Ant Design 5 构建，最终形态是**一套后台 + 多端前台（Web/H5/开放 API）**的内容中台。

### 1.2 总体目标

| 维度 | 目标 |
| --- | --- |
| 管理侧 | 让运营/编辑人员在无研发介入的前提下完成内容全生命周期管理 |
| 权限侧 | 细粒度 RBAC（菜单级 + 按钮级 + 字段级），满足多人多角色协作 |
| 内容侧 | 从「能存能发」升级为「好用、好看、可复用、可运营」 |
| 分发侧 | 一套内容多端复用，支持前台站点、开放 API、静态化与 SEO |
| 用户侧 | 建立 C 端用户体系（注册登录、个人中心、收藏评论），以等级 + 积分沉淀可运营的用户资产 |
| 工程侧 | 可测试、可观测、可持续集成，支撑长期迭代 |

### 1.3 分期总览

| --- | --- | --- | --- | --- |

**前端（`web/`）**

| 项 | 选型 |
| --- | --- |
| 框架 | React 18.3 + Vite 5 |
| UI | Ant Design 5.21 + @ant-design/icons 5 |
| 路由 | react-router-dom 6（HashRouter） |
| 图表 | ECharts 5（`components/EChart.jsx` 封装） |

### 2.2 已交付功能清单

**认证与账号**

- 登录（`POST /api/auth/login`）：bcrypt 校验、禁用/软删除拦截、记录最后登录 IP 与时间
- 登录返回：`token` + `admin` + `permissions` + `menus`（菜单树由权限动态生成）
- 拉取当前用户信息 `GET /api/auth/profile`、退出 `POST /api/auth/logout`
- 修改密码 `POST /api/auth/password`（校验原密码，新密码 ≥ 6 位）

**RBAC 权限体系（三层校验）**

| 层级 | 实现 | 位置 |
| --- | --- | --- |
| 接口级 | 中间件按「请求方法 + 路径」匹配权限点 | `app/middleware/Auth.php` + `config/auth_route.php` |
| 操作级 | 控制器内 `$this->checkPermission('content.create')` | `app/BaseController.php` |
| 字段级 | 改动 `status` / `is_top` 需各自独立权限点 | `ContentController::checkFieldChange()` |
| 前端级 | `hasPermission()` 控制按钮与菜单显隐 | `web/src/store/AuthContext.jsx` |

数据模型：管理员 →（主组 `admin.group_id` + 附加组 `auth_group_access`）→ 用户组 `auth_group.rules` → 权限菜单 `auth_rule`（`type=1` 菜单 / `type=2` 权限点）。任一用户组 `rules='*'` 即超管；`admin.id=1` 内置保底超管。

**内容管理**：列表（关键词/分类/状态/置顶/日期区间筛选 + 多字段排序 + 分页）、新增、编辑、软删除、批量删除、发布/下架、置顶/取消置顶；写入字段白名单、发布时间自动补全。

**分类管理**：树/列表、新增、编辑、删除、启停用、下拉选项接口。

**系统管理**：管理员 CRUD + 启停用、用户组（角色）CRUD + 权限授权（`PUT /api/group/:id/rules`）、权限菜单 CRUD + 启停用。

**数据看板**：8 张指标卡（内容总数/已发布/草稿下架/累计浏览/今日/本月/分类数/管理员数）+ 状态分布 + 分类分布 + 近 14 天新增趋势 + 热门 TOP8 + 最新内容 + 最近日志。

**操作日志**：分页查询（模块/动作/管理员/时间筛选）、清空日志；所有写操作均落 `zsk_operation_log`。

## 三、第二阶段：内容生产能力升级

## 四、第三阶段：前台站点、用户体系与内容分发

**周期建议**：2027.01 – 2027.03　**预估**：约 55 人日（含 C 端用户体系约 20 人日）

### 4.1 阶段目标

打通「生产 → 消费 → 沉淀用户」闭环：

1. 后台内容以**站点 + 开放 API** 两种形式对外交付，具备基础的流量运营与 SEO 能力；
2. 建立**独立的 C 端用户体系**（注册、登录、个人中心），让用户能够收藏、评论并与内容互动；
3. 通过**等级 + 积分**成长体系把用户行为沉淀为可运营的资产，为后续精细化运营与权益体系打底。

衡量指标：前台上线后注册转化率、人均评论/收藏次数、日活用户留存构成该阶段的核心观察指标。

### 4.2 功能范围 — A. 内容分发

| 编号 | 功能 | 说明 |
| --- | --- | --- |

| 3.2 | 开放内容 API | `GET /api/open/...`：分类列表、内容列表、内容详情；AppKey + 签名鉴权，与后台 JWT、C 端用户 Token 三套体系隔离 |

### 4.5 用户体系关键技术点

- **双 Token 体系**：C 端签发 `user` 角色 JWT（复用 `app/service/Jwt.php`，payload 增加 `role=user`），中间件 `app/middleware/UserAuth.php` 校验；Refresh Token 用于无感续期，登出/封禁时加入短期黑名单
- **密码与验证码**：密码统一 bcrypt；短信/邮箱验证码 60s 冷却、当日上限、服务端校验不回显具体错误；图形验证码接入登录与注册
- **积分与经验并发**：积分变更走事务 + 行锁（`lock(true)`），流水与余额同事务写入；经验变更后同步计算等级并写入升级消息
- **评论安全**：提交内容 HTML 白名单过滤、敏感词库匹配、频率限制（同用户 N 秒一条）、先审后发开关；评论列表防刷分页
- **内容互动计数**：`content` 表扩展 `favorite_count` / `comment_count` 冗余字段，异步校正，避免列表页实时 count
- **隐私合规**：手机号/邮箱脱敏展示，注销走软删除 + 冷却期后可恢复，导出个人数据能力预留

### 4.6 内容分发关键技术点

- 前台只读库查询与后台写库分离（读写分离或只读连接）
- 内容详情 HTML 输出二次过滤，防止后台编辑引入脚本
- 缓存一致性：内容发布/下架/删除时主动清除对应缓存 key
- 开放 API 限流（令牌桶），密钥可轮换

### 4.7 交付物与验收标准

- 交付：前台站点工程（首页/分类/详情/搜索/登录注册/个人中心/收藏/评论/等级积分页）、用户中心后端模块（User / Comment / Favorite / Points 控制器与模型）、后台用户管理页面、新增表迁移 SQL、接口文档
- 验收：
  - 注册→登录→浏览→收藏→评论→获取积分→升级 全链路可走通，未登录访问受限接口返回 401
  - 同一文章重复收藏幂等，取消收藏后计数正确回落
  - 评论先审后发开关生效，敏感词命中进入待审；举报可在后台处理
  - 积分流水与余额始终一致（并发积分发放压测下无负数、无丢失）
  - 后台发布内容 60 秒内前台可见；开放 API 无密钥调用被拒；移动端主流分辨率无错位；首页首屏 < 2s

### 5.3 关键技术点

- 数据权限：在 `BaseController` 层注入站点/部门维度的数据过滤，与功能权限解耦
- 状态机：内容状态与审核状态分离，避免互相污染
- 定时任务：命令 `php think content:schedule` / `php think user:points-expire` + 系统 cron，需防并发执行（文件锁）
- AI 调用：异步队列 + 超时降级，避免阻塞管理端请求；记录调用成本与审计日志
- 积分与权益事务：兑换走「扣减积分 + 生成订单 + 扣减库存」同事务，失败整体回滚；积分过期由定时任务批量处理并留痕
- 用户分群：离线计算分群结果入 `zsk_user_segment`，线上仅查结果表，避免实时大表扫描

### 5.4 交付物与验收标准

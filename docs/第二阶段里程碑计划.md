## 一、目标与验收口径

**阶段目标**：让内容从「能存能发」升级为「好用、可复用、可恢复」。

**量化口径**（阶段出口以此为准）：

| 指标 | 阶段前基线 | 阶段目标 | 度量方式 |
| --- | --- | --- | --- |
| 单篇内容平均编辑耗时 | 48.8 分钟（加权基线，由度量脚本建模得出） | **分项**：图文混排 ≥30%、含表格 ≥20%、加权 ≥20%（2026.10.30 评审修订；原「整体下降 40%」口径作废） | `php scripts/measure_edit_efficiency.php --demo`；库内内容积累后去掉 `--demo` 重跑取实测值 |
| 误删内容可恢复率 | 0% | 100% | 删除 → 回收站 → 恢复，字段级比对 |
| ~~编辑留痕覆盖率~~ | 0% | ~~100%（每次保存均有版本）~~ **指标作废**：版本功能已于 2026.10.30 下线（见 11.12.9） | — |
| XSS 拦截率 | 0% | 100% | 20 条攻击样本全部被净化 |

**非目标（本阶段不做）**：前台站点、C 端用户体系、协同编辑、AI 辅助、缓存/性能治理——均属第三至五阶段。

**编辑效率度量结果**（替代原「人工计时基线」，原因与模型见下文；结论：**按 2026.10.30 评审通过的分项口径，三项全部达标**）

| 内容形态 | 改造前（分钟） | 改造后（分钟） | 下降幅度 |
| --- | --- | --- | ---: |
| 纯文字短文 | 14.6 | 12.3 | 15% |
| 图文混排 | 50.8 | 35.2 | **31%** |
| 含表格 | 20.7 | 15.8 | **24%** |
| 长文（2000 字+） | 106.0 | 84.6 | 20% |
| 转载排版 | 52.0 | 43.5 | 16% |
| **加权均值** | **48.8** | **38.3** | **22%** |

> 原计划在编辑器上线前人工计时采集基线，**该窗口在 M2.2 落地时已经失效，无法补采**。
> 替代方案：把编辑耗时建模为「编辑者必须产生的输入量」，用可随时重跑的脚本度量 ——
> `php scripts/measure_edit_efficiency.php --demo`（代表性样本）或去掉 `--demo`（读取库中实际内容）。
>
> **为什么只有 22%，而不是 40%**：以文字为主的内容，编辑时间本来就花在「打中文」上，
> 这部分在任何编辑器里都无法省。富文本编辑器真正省掉的是手写 HTML 标签、肉眼排错、
> 以及配图要外部找链接这三类开销，它们的占比决定了总降幅的上限。
> 收益也因此高度集中在 **图文混排（31%）与含表格（24%）** 两类。
> 该结论对「打字速度」等单价设定不敏感——单价变动会同步放大两边，比值基本不变。
>
> **评审结论（2026.10.30，已采纳）**：整体 40% 目标作废，改为分项口径。
> 原建议阈值统一取 25%，但含表格类实测 **24%**（差 1 个百分点，折合约 15 秒/篇）：
> 该类内容耗时基数最小（20.7 分钟）、绝对节省 4.9 分钟，用同一阈值衡量并不公平，
> 故最终定为 **图文混排 ≥30% / 含表格 ≥20% / 加权 ≥20%**，三项实测均达标。
> 待库里积累真实内容后，不带 `--demo` 重跑脚本即可替换为实测值。
>
> **新增出口项**：可用性验收 —— 非运营人员能否独立完成排版（任务清单见 11.12.6）。

**后端（3 人日）**
- `app/service/HtmlFilter.php`：封装 HTMLPurifier 标签/属性白名单
  - 允许：`p br strong em u s h1-h4 ul ol li blockquote pre code table thead tbody tr th td a img figure figcaption hr span`
  - `a`：强制 `rel="nofollow"`，`href` 协议仅 http/https/mailto
  - `img`：协议仅 http/https（禁 `javascript:`、`data:` 外的内嵌脚本）
  - 事件属性（`on*`）一律剥离；`style` 自 2026.10.30 起**按 CSS 属性白名单放行**（图片缩放要用），
    `position` / `z-index` / `expression()` / `url()` 等危险取值仍会被清除，详见 11.12.7
- `ContentController::save/update` 入库前净化；`read` 输出时二次净化（防历史脏数据）
- 内容列表摘要回显仍走纯文本截断，不输出 HTML
- 净化失败的降级策略：抛业务异常并阻止保存，不做静默放行

**验收**
- 粘贴 Word / 网页富文本后标签收敛到白名单内，样式被剥离
- 20 条 XSS 样本（`<script>`、`onerror`、`<img src=javascript:>`、`svg onload` 等）入库后全部失效
- 编辑器保存 → 重新打开 → 回显 100% 一致（含表格、代码块、图片）
- 图片上传 → 插入 → 保存 → 回显链路贯通

## 七、关键技术决策（ADR）

| 编号 | 决策 | 结论 | 理由 / 备选 |
| --- | --- | --- | --- |
| ADR-001 | 富文本编辑器 | **WangEditor 5** —— 已定稿并安装：`@wangeditor/editor@5.1.23` + `@wangeditor/editor-for-react@1.0.6` | MIT 协议、中文生态、体积小、无商业限制；备选 TinyMCE（功能更全但体积大） |
| ADR-002 | 后端 HTML 净化 | **`ezyang/htmlpurifier`**（4.19.0，已安装并作为主路径） | 成熟白名单引擎；`HtmlFilter` 采用双引擎结构，依赖缺失时自动回落到自研 DOM 过滤，业务代码无需感知 |
| ADR-003 | 文件存储磁盘 | **`public` 磁盘**（`public/storage`，URL `/storage`） | 现用 `runtime/storage` 无法直接对外访问；需配套上传目录禁解析配置 |
| ADR-004 | ~~版本存储策略~~ | ~~全量快照 + 每篇 20 条滚动淘汰 + 自动保存 30 分钟合并~~ **已作废**（版本功能 2026.10.30 下线，见 11.12.9） | 原理由：内容量小（千级），全量简单可靠；后续量大可切增量 diff |
| ADR-005 | 标签存储 | **独立关联表**，旧 `tags` 字段一次性迁移后保留（不再写入） | 支持标签云、计数与筛选；逗号字段无法支撑运营 |
| ADR-006 | 导入导出格式 | **CSV 优先（零依赖），Excel 可选** | 避免引入 PhpSpreadsheet 依赖成本，按需再扩展 |
| ADR-007 | ~~版本操作权限~~ | ~~并入 `content.update`，不新增权限点~~ **已作废**（版本功能 2026.10.30 下线） | 原理由：控制权限点膨胀，降低授权配置成本 |
| ADR-008 | ~~编辑冲突处理~~ | ~~乐观提示（409 + 版本号比对），不做协同编辑~~ **已作废**：依赖版本号比对，随版本功能下线；且该机制未实现 | 协同编辑成本远超本阶段收益 |

### 11.10 内容列表菜单入口丢失（2026.10.30 修复）

#### 11.12.3 缺陷：一次改动打挂全部上传

新增「单请求整体大小上限」时写成
`$this->request->server('CONTENT_LENGTH', 0)`，而 ThinkPHP 8 的 `Request::server()`
第二个参数声明为 `string`，传整型直接抛 `TypeError` → **上传接口全部 500**。

- 暴露方式：`php -l` 与 `npm run build` 都通过，只有端到端发一次上传请求才复现
- 修复：`(string) $this->request->server('CONTENT_LENGTH', '0')`，并就地注释参数类型约束
- 教训：与 11.3 同源——**静态检查只能证明"能编译"**。凡是涉及类型签名、响应契约、
  跨层约定（如 wangEditor 的 `errno`）的改动，必须补一次真实请求；本轮已把
  「上传 → 分组 → 移动 → 回收站详情」串成一条 curl 回归链，可重复执行。

#### 11.12.7 缺陷：图片缩放尺寸保存后丢失（2026.10.30）

**现象**：编辑器里把图片拖小 → 保存 → 重新打开，图片又变回原尺寸。

**原因**：WangEditor 把缩放结果写成内联 `style="width: 300px"`，
而净化白名单里 `img` 只允许 `src|alt|title|width|height`，**style 被整条剥离**。
段落居中、文字颜色、行高等写在 style 上的排版，同样会被静默丢掉。

**为什么回归没发现**：原用例断言的是「输出中不允许出现 style」，
等于把「该留的样式被误删」也判成了通过——白名单类改动只测了「危险的进不来」，
没测「该留的出得去」。

**修复**：放行 style，但取值收敛到 CSS 属性白名单：

| 层 | 做法 |
| --- | --- |
| 共用白名单 | `HtmlFilter::CSS_PROPS`：尺寸 / 间距 / 对齐 / 文字外观 / 边框；排除 `position`、`z-index`、`transform`、`filter`、`opacity`、`display`、`background`（简写可带 `url()`）等 |
| HTMLPurifier | `CSS.AllowedProperties`；`HTML.DefinitionRev` 3 → 4（不递增会命中旧的定义缓存） |
| 自研兜底 | 新增 `sanitizeStyle()`：逐条声明过滤 + 危险词黑名单（`expression`/`behavior`/`url(`/`&#`/反斜杠）+ 取值形状校验；过滤后为空则整条移除，不留空壳 |

| 输入 | 输出 |
| --- | --- |
| `<img src="/storage/a.jpg" style="width:300px;height:200px">` | `style="width: 300px; height: 200px"` |
| `<p style="text-align:center">居中段落</p>` | 原样保留 |
| `<img … style="position:fixed;…;z-index:99999;width:100%">` | 仅剩 `width: 100%` |

### 11.13 侧边栏登录时默认收起子菜单（2026.10.30）

**诉求**：登录后侧边栏的分组（内容管理 / 系统管理）不要预先展开。

**根因**：11.12.1 做的「展开状态持久化」把 `openKeys` 写进 localStorage（`zsk_menu_open_keys`），
`BasicLayout` 挂载时原样读回。`logout()` 里有清理，但**登录路径（`setSession`）没有**——
于是上一个账号展开过的分组会被下一个账号原样继承；走 401 跳登录、或直接关浏览器再进来同理。

**修复**：

| 位置 | 改动 |
| --- | --- |
| `AuthContext.setSession` | 登录即清空 `zsk_menu_open_keys`，每次登录都从全部收起开始 |
| `BasicLayout` | 菜单数据到位后，用 `collectParentKeys()` 剔除缓存里已不再存在的容器 key，作为菜单结构变动的兜底；不干扰用户手动展开的记录 |

**仍保留的行为**（这三者不冲突）：

- 会话内手动展开的分组照旧持久化，**刷新后保持** —— 这是 11.12.1 的初衷
- 进入二级菜单页（如 `/content/trash`）时仍自动展开**该条分支**，否则高亮会被折叠起来看不见
- 自动展开的那一条**不写回缓存**（`setOpenKeys` 不触发 `onOpenChange`），不会被记成用户偏好

即「默认收起 / 当前所在分支可见 / 会话内记住手动选择」并存。

**无需跑 SQL、无需重启后端**，重新构建前端即可。
注意：**退出再登录**才生效——单纯刷新页面不会清缓存（那正是"会话内保持"的设计）；
想立刻查看可在控制台执行 `localStorage.removeItem('zsk_menu_open_keys')`。

#### 踩到一个权限提升陷阱（本次真正的风险点）

改完 pid 后核对各组权限，**只读访客组的权限点从 6 个涨到了 14 个**——
多出 `content.create / update / delete / batch-delete / status / top / export / copy`
八个写操作，只读账号拿到了全部内容操作权。

根因在 `Permission::keysByRuleIds()`：

```php
$walk = function (int $id) use (&$walk, &$owned, $all): void {
    $owned[$id] = true;
    foreach ($all as $rule) {
        if ((int) $rule['pid'] === $id) { $walk((int) $rule['id']); }
    }
};
```

它对 `rules` 里的每个 id **递归展开整棵子树**——即「授予菜单 ID」等价于
「授予该菜单下全部权限点」。`#201` 原本是叶子，展开它只标记自己；上面一步给它挂了
9 个子节点后，`rules` 里含 `201` 的组就全都被放大了。

两点值得记住：

1. **改 `pid` 不是纯展示改动**。它改变了「菜单 → 权限集合」的外延，
   只要把叶子节点变成枝干，就会连带改变所有引用它的用户组的实际权限。
   事前分析时我只核对了 `filterMenuTree()` 的可见性，没核对 `keysByRuleIds()` 的展开，于是漏了。
2. **做法是配套剔除**：把菜单 `#201` 从各用户组 `rules` 中整体移除（脚本第 2 段，幂等）。
   剔除后菜单仍在——`#201` 自身 `name=content.list`，这些组都另行授权了 `#21`，
   `filterMenuTree()` 的 `selfOwned` 判定会保住它。

**验证**（迁移前后逐一比对，完全一致才算过）：

| 用户组 | 迁移前权限点 | 迁移后（未剔除 201） | 迁移后（已剔除 201） | 结论 |
| --- | ---: | ---: | ---: | --- |
| #2 内容运营 | 26 | 26 | **26** | 一致 ✅ |
| #3 只读访客 | 6 | **14** ❌ | **6** | 修复后一致 ✅ |

可见菜单两组迁移前后均保持 6 个（`/#content` 仍在），接口回归 `code=0`。

本次未改。给只读角色授权时请展开后只勾选具体的读权限点，不要直接勾菜单。

#### 顺带修掉同一个根因的两个缺陷

| 字段 | 原来 | 后果 |
| --- | --- | --- |
| `publish_time` | `buildPayload()` 末尾无条件落到 `else { = null }`；且 `status=1` 时空值会被填成当前时间 | 只改标签 / 只改状态的局部更新，会把已有发布时间**静默重置为当前时间**或**清空**。实测一次改标签操作把 8 篇的发布时间全部刷成了同一时刻 |

**修复**（`ContentController`）：

- `buildPayload(array $data, ?array $old = null)` 增加 `$old`；
  `publish_time` **只有显式传入才处理**，不传则保持原值
- 自动补充发布时间的条件收紧为「原本就没有时才填充」，不再覆盖既有值
- `tags` 同步改为 `if (array_key_exists('tags', $data))`；
  传空数组仍表示「清空全部标签」，语义不变

**前端主流程本来不受影响**：编辑页与自动保存都会显式带上 `publish_time` 与 `tags`。
缺陷只在 API 局部更新场景暴露——但既然存在，且已经咬到人，就一并修了。

| 新建已发布且不传 | 自动填充当前时间 | 已填充 ✅ |
| 显式传 `null` | 清空 | NULL ✅ |

另跑通：XSS 净化 39 条、列表 / 详情 / 看板 / 标签筛选 / 分类筛选 / 素材库接口均 `code=0`，

### 11.16 有内容的分类不允许删除：补齐前端拦截（2026.10.30）

**诉求**：分类管理中，分类下有内容时不允许删除。

**后端一直都有这道防线**（`CategoryController@delete`）：删除前统计 `category_id` 匹配的
未软删内容数，`> 0` 直接 fail。通道也只有一条（`DELETE /category/:id`，**没有批量删除**），
所以数据安全上从来没有缺口。

**缺的是前端**：`CategoryList` 的删除按钮不看内容数，一律可点，用户要点完才被后端驳回。

**改动**

| 位置 | 内容 |
| --- | --- |
| `web/src/pages/CategoryList.jsx` | `used > 0` 时删除按钮 `disabled` 并用 Tooltip 说明原因；`= 0` 时保持 Popconfirm 二次确认 |
| `CategoryController@delete` | 错误文案与前端 Tooltip 对齐——原来是「，无法删除」，现统一为「，请先移走或删除后再删除该分类」 |

**为什么分类页用 Tooltip，而不是照抄标签页**：
`TagList.jsx` 早有同类处理（`disabled={Number(row.count) > 0}`），
但它的提示写在 `Popconfirm.description` 里——**按钮被禁用后 Popconfirm 打不开，
那段描述用户永远看不到**。所以分类页改用 Tooltip，悬停即知原因。
（同理 `AttachmentController` 也有引用保护，前端情况未做调整，本次未动。）

**验证**（API 层 3 个用例全过）

| 用例 | 结果 |
| --- | --- |
| 删除有内容的分类（#1 人工智能，2 条） | `code=1` 已拒绝，文案含具体条数 ✅ |
| 删除无内容的分类 | `code=0` 删除成功 ✅ |
| 删除后再读 | `404 分类不存在或已删除` ✅ |

改动前后均已回归：前端构建通过，测试数据全量清理（无残留临时分类）。

**遗留发现（本次未改）**：`zsk_category.slug` 的唯一索引**连同软删记录一起占位**——
软删一个分类后，它的标识无法再被新分类复用。`save()` 不做重复校验，
冲突直接发生在数据库层表现为新增失败（拿不到 id）。遇到时换个 slug 即可。

### 11.17 编辑内容时分类下拉显示全部，禁用项置灰不可选（2026.10.30）

**诉求**：编辑内容页的「所属分类」要列出全部分类（含禁用），
禁用的显示为 disabled 状态、不允许选择。

**问题**：`GET /category/options` 原本写死只返回 `status = 1`，
禁用分类根本不进下拉——这不只是「看不到」。

**为什么必须把禁用项列出来，而不只是过滤掉**：
若某条内容当前所属的**正是**禁用分类，下拉里没有这一项，
Form 的 `category_id` 就找不到对应 option，界面回显成空白或裸数字 id。
用户此时只要点一下保存，分类就会被悄悄改掉。
展示为「禁用且不可选」既能看清现状，又不会误改。

**改动**（三处）

| 位置 | 内容 |
| --- | --- |
| `CategoryController@options` | 新增 `include_disabled` 参数：默认仍只返回启用；传 `1` 时连同禁用一起返回 |
| `web/src/api/index.js` | `categoryApi.options(params)` 支持传参，不传时行为与原来完全一致 |
| `ContentEdit.jsx` | 取数传 `include_disabled: 1`；`status !== 1` 的项加 `disabled: true`，label 追加「（已禁用）」 |

**为什么用参数隔离，而不是直接放开 `options`**：
这个接口有第二个使用方——**内容列表的分类筛选**（`ContentList.jsx`）。
那里仍然只该列出启用分类，所以保留默认行为，由编辑页显式开关。

关于回显：antd Select 的 `disabled` **只拦截交互**，已经选中的禁用项依然正常显示名称，
所以「内容所属的禁用分类」在下拉里能看到名字，只是不能再点选它。

**验证**（5 个用例全过）

| 用例 | 结果 |
| --- | --- |
| 默认 `options` | 返回 5 个，禁用分类 #6 不在其中 ✅（列表筛选不受影响） |
| `include_disabled=1` | 返回 6 个，含 #6 ✅ |
| 返回项带 `status` | `status=0` ✅（前端据此置灰） |
| 属于禁用分类的内容重新读取 | `category_id` 未变 ✅ |
| 原样执行一次编辑保存 | 分类没被冲掉 ✅ |

测试结束后分类 #6 已恢复启用；内容 10 条、无一例外地落到有效分类上。

**未改动**：内容列表的分类筛选下拉仍只显示启用分类。若日后希望筛选也能按禁用分类检索
（确实存在属于禁用分类的历史内容），单独放开那一处即可。
